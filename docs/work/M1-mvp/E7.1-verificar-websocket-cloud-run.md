# E7.1 — Verificar que Cloud Run sostiene el WebSocket

## Cambio

Comprobar, con una sola instancia en Cloud Run, que un WebSocket aguanta conexiones largas y que la
reconexión no hace falta más de una vez cada 60 minutos (R1). Se hace con un endpoint WebSocket
temporal de prueba (eco o latido) desplegado en el servicio actual. Se mide la duración de la
conexión y cada corte que ocurra.

Es el primer paso de la épica, sin dependencias. Como tarda al menos 60 minutos de reloj, arranca al
principio y corre en paralelo a E7.2 y E7.3.

## Dónde cae

- `apps/backend/`: endpoint temporal, que se borra al terminar la prueba.
- Despliegue con `scripts/desplegar-backend.sh` sobre el servicio de Cloud Run existente, con
  `max-instances=1`.

## Debe ser cierto después

- Hay un resultado registrado: la conexión duró al menos 60 minutos sin corte, o se midió cada corte
  con su intervalo. Dónde se registra el resultado, a definir en el issue.
- Si la conexión no se sostiene, el issue no se da por terminado. Se abre una decisión con el usuario
  para repensar el canal. E7.5 no arranca hasta que eso esté resuelto.
- El endpoint temporal no queda en el repo. `dart analyze` y `dart test` del backend siguen limpios.

## Restricciones

- Se comprueba en la práctica, no se supone (épica E7, "Contingencia").
- Sin APIs específicas de Google en el backend (CLAUDE.md), para que la misma imagen pueda salir de
  Cloud Run.
- Código nuevo en inglés (CLAUDE.md).

## Bloqueos externos

- Desplegar requiere `gcloud auth login` del usuario en su máquina.

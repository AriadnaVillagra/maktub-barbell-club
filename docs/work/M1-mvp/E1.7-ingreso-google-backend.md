# E1.7 — Endpoint de ingreso con Google

## Cambio

Agregar el endpoint de ingreso que recibe el ID token de Google, verifica el email contra los usuarios dados de alta, guarda el `sub` en el primer ingreso y abre la sesión propia con `StartSession`.

## Dónde cae

- `apps/backend/lib/features/auth/start_session/start_session.dart`: el slice existe pero no tiene endpoint (findings, 1.2). Este issue lo llama.
- `apps/backend/routes/auth/`: ruta nueva de ingreso, junto a `refresh.dart` y `logout.dart`.
- Slice de ingreso con su store: buscar usuario por email normalizado y guardar el `sub`.
- Verificador de E1.6.
- `apps/backend/lib/infraestructura/http.dart`: `ErrorDeSolicitud` para el rechazo.

## Debe ser cierto después

- Un token válido de un email dado de alta devuelve la sesión (access y refresh) y guarda el `sub` en el primer ingreso.
- Un email sin cuenta recibe un rechazo con mensaje claro y un código 4xx distinto de 401. El código exacto lo elige el issue y queda anotado.
- Un token inválido o con email no verificado se rechaza sin crear sesión.
- Ningún ingreso crea usuarios nuevos.
- Tests con store fake y verificador fake.

## Restricciones

- F1 §5 › Identidad: un email sin cuenta recibe un rechazo que no es 401, porque la app trata 401 como "renovar el token".
- F1 §5: el email identifica al usuario. Vincular con cuentas de contraseña queda fuera (F1 resto).
- design.md §4.1: va después de E1.2, antes de que haya usuarios reales con sesión.
- CLAUDE.md › Backend: vertical slices; el store expone solo lo que usa este slice.
- Código nuevo en inglés (CLAUDE.md, intro).

## Decisiones cerradas

- Email desconocido: rechazo claro, código distinto de 401 (F1 §5).
- Los usuarios se crean solo por el script de alta (E1.9). El registro queda fuera (F1 resto).

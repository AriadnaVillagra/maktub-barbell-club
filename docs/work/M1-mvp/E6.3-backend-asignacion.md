# E6.3 — Backend: asignar un plan a un grupo

## Cambio

Agregá el slice de asignaciones en `apps/backend/lib/features/asignaciones/`, con tres casos de
uso: crear una asignación (plan × grupo × fecha de inicio, queda activa), terminarla y listar
las asignaciones del club o de un grupo. Cada uno tiene su store con la interfaz y la
implementación Mongo, y la colección lleva índice por `clubId`.

## Dónde cae

- `apps/backend/lib/features/asignaciones/` (slices y stores).
- `routes/` solo despacha por método HTTP.
- Tests con stores falsos en `apps/backend/test/features/asignaciones/`.

## Debe ser cierto después

- Crear deja la asignación activa. Terminar la pasa a terminada. Nada se borra.
- Un grupo tiene a lo sumo una asignación activa. Crear una segunda para el mismo grupo devuelve
  un 4xx con `{error}`. Para reemplazar, el coach termina la activa y después crea la nueva.
- Escribir exige `Accion.planificar` (solo coach). Leer exige `Accion.verCatalogoYPlanes`.
- Todas las consultas filtran por `clubId`, y el test de aislamiento de E1.11 corre sobre cada
  endpoint.
- Un plan o un grupo de otro club se rechazan con 4xx y `{error}`.
- La fecha de inicio llega como `yyyy-MM-dd` y se guarda como fecha UTC.
- `dart test` y `dart analyze` limpios en `apps/backend`.

## Decisiones cerradas

- Escribir asignaciones es `Accion.planificar` (matriz de `puede()`: "planificar, asignar").
- Quien termina una asignación regular es el coach (ver E6.1). El fin de ciclo no la termina.
- Un grupo tiene a lo sumo una asignación activa (D14).

## Restricciones

- Pregunta abierta: ¿la asignación terminada guarda fecha de fin? Ver E6.1.
- La validación del plan (que exista en el club) usa un store propio de este slice, con la
  lectura mínima de E5. No se comparte repositorio (CLAUDE).

## Bloqueos externos

Ninguno fuera de M1.

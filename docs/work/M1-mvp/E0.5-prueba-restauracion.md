# E0.5 — Probar la restauración del backup en local

## Cambio

Bajar un dump del bucket, restaurarlo en la MongoDB local de docker compose y comparar sus datos con los de origen.

## Dónde cae

- `docker-compose.yml`: MongoDB local en `localhost:27017`.
- `apps/backend`: el `MONGO_URL` por defecto (`mongodb://localhost:27017/maktub`) apunta a esa base; la API no cambia.
- Sin cambios en el repo salvo que el ejecutor decida dejar un script de restauración; las fuentes no lo piden.

Es una prueba manual con evidencia, no código nuevo.

## Debe ser cierto después

- `mongorestore` del dump más reciente termina sin error en la base local.
- Los datos restaurados coinciden con los de origen según un criterio de comparación que el ejecutor define y deja escrito (ver nota en el reporte de la épica; las fuentes no fijan el criterio).
- El dump restaurado es el de un job que corrió con éxito (E0.4), no uno armado a mano.

## Restricciones

- design.md §3.5: el backup es `mongodump`; la restauración se prueba contra la base local, no contra producción.
- CLAUDE.md › Commands: la base local se levanta con `docker compose up -d`.
- E0 › Terminada cuando: "se restauró uno en una base local y los datos coinciden".

## Bloqueos externos

- Ninguno fuera de E0.4 si hay un dump en el bucket.

## Resultado (2026-11-07)

Hecho, con un dump del job `maktub-backup` (ejecución `maktub-backup-67qcf`,
`maktub-2026-11-07T175609Z.archive.gz`).

- **Cómo se restaura**, en una base aparte para no pisar la de desarrollo:
  `docker compose exec -T mongo mongorestore --archive --gzip --nsFrom='maktub.*' --nsTo='maktub_restore.*' --drop < <dump>`.
  Terminó sin errores.
- **Criterio de comparación:** mismas colecciones, misma cantidad de documentos por colección y mismos
  nombres de índices que la base de producción en el momento del dump. Coinciden:
  `login_sessions`, 0 documentos, índices `_id_` y `userId`.
- **Hallazgo y arreglo:** el secreto `mongo-url` no traía nombre de base, así que producción usaba
  `test`. Se agregó la versión 2 del secreto con `/maktub` y se redesplegó la API (revisión
  `maktub-api-00007`). `test` quedó vacía y sin uso. Producción no tenía datos, así que no se perdió
  nada.
- **Límite de la prueba:** la base todavía está casi vacía. La restauración con datos reales se
  vuelve a comprobar en E8 y en el corte (E9).
